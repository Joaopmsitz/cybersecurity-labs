# Activity 10.05 — Suricata on Kali Linux

## Objective

Configure and run Suricata on Kali Linux, using detection rules to monitor network traffic and examining the log files generated by the engine.

## Environment

- **System:** Kali GNU/Linux Rolling
- **Tool:** Suricata
- **Version:** 8.0.2
- **Monitored network interface:** `eth0`
- **Access:** RDP

The credentials used to access the lab are not included in this README.

## 1. Opening the Terminal as Root

After accessing the Kali Linux machine, a terminal was opened and the following command was executed:

```bash
sudo -i
```

The terminal then operated with administrative privileges.

## 2. Enabling the Suricata Service

Automatic startup of the service was enabled:

```bash
systemctl enable suricata.service
```

**Output:**

```text
Created symlink '/etc/systemd/system/multi-user.target.wants/suricata.service' → '/usr/lib/systemd/system/suricata.service'.
```

This command creates the necessary systemd link so that Suricata starts automatically according to the service configuration.

## 3. Stopping the Service and Downloading the Rules

First, the service was stopped:

```bash
systemctl stop suricata.service
```

Next, the rules directory was accessed:

```bash
cd /var/lib/suricata/rules/
```

The `emerging-exploit.rules` file was downloaded:

```bash
wget https://raw.githubusercontent.com/seanlinmt/suricata/master/files/rules/emerging-exploit.rules
```

**Output:**


After the download, the terminal returned to the home directory:

## 4. Configuring `suricata.yaml`

The main Suricata configuration file was opened:

```bash
nano /etc/suricata/suricata.yaml
```

The setting related to the rules directory was located inside the file.

The original configuration used in the lab was:

```yaml
default-rule-path: /var/lib/suricata/rules

rule-files:
  - suricata.rules
```

It was changed to use the downloaded rules file:

```yaml
default-rule-path: /var/lib/suricata/rules

rule-files:
  - emerging-exploit.rules
```

After making the change, the file was saved and the editor was closed.

This configuration instructs Suricata to look for rules in the following directory:

```text
/var/lib/suricata/rules
```

and specifically load:

```text
emerging-exploit.rules
```

> **Verification note:** The `wget` output shows that the downloaded file was saved as `emerging-exploit.rules.1`, while the configuration references `emerging-exploit.rules`. If a file with the original name already existed, Suricata may have loaded that existing file rather than the newly downloaded copy. Verify the filenames and confirm which rules file was loaded.

## 6. Running Suricata

After configuring the rules and identifying the network interface, Suricata was started directly from the terminal:

```bash
suricata -c /etc/suricata/suricata.yaml -i eth0
```

**Output:**

```text
i: suricata: This is Suricata version 8.0.2 RELEASE running in SYSTEM mode
W: detect-flowbits: flowbit 'ET.pdf.in.http' is checked but not set. Checked in 2017790 and 0 other sigs
i: mpm-hs: Rule group caching - loaded: 0 newly cached: 13 total cacheable: 13
i: threads: Threads created -> W: 2 FM: 1 FR: 1   Engine started.
```

The output confirms that Suricata version 8.0.2 started and began running on the `eth0` interface.

A warning was also displayed concerning a flowbit referenced by a rule:

```text
W: detect-flowbits: flowbit 'ET.pdf.in.http' is checked but not set.
```

Despite the warning, the engine continued its initialization normally, as indicated by:

```text
Engine started.
```

## 7. Checking the Log Files

While Suricata was running, a second terminal was used to inspect the generated log files.

The following directory was accessed:

```bash
cd /var/log/suricata
```

Then the following command was executed:

```bash
ls
```

**Output:**

```text
eve.json fast.log stats.log suricata.log
```

The directory contained the following files:

- **`eve.json`** — Structured events generated by Suricata.
- **`fast.log`** — A simplified record of alerts.
- **`stats.log`** — Runtime statistics.
- **`suricata.log`** — Logs related to the engine's operation.

## 8. Stopping Suricata

After checking the log files, the Suricata process was stopped in the first terminal using:

```text
Ctrl+C
```

**Output:**

```text
i: suricata: Signal Received. Stopping engine.
i: device: eth0: packets: 8624, drops: 0 (0.00%), invalid chksum: 0
```

Suricata received the interrupt signal and shut down the engine.

The following statistics were recorded during execution:

```text
packets: 8624
drops: 0 (0.00%)
invalid chksum: 0
```

These results indicate that 8,624 packets were processed during this run, with no packets dropped by the engine and no invalid checksums reported.

## Key Concepts

- **Suricata:** A network threat detection and prevention engine used to monitor network traffic.
- **Rules:** Definitions used to identify specific patterns and behaviors in network traffic.
- **`eve.json`:** The primary structured event log.
- **`fast.log`:** A simplified alert log.
- **`stats.log`:** Runtime statistics.
- **`suricata.log`:** Operational logs generated by the engine.


## Result

Suricata was configured to use the `emerging-exploit.rules` file and was run on the `eth0` network interface.

The engine started successfully, and log files were generated in `/var/log/suricata`. At the end of the run, 8,624 packets were recorded, with 0 drops and 0 invalid checksums.
