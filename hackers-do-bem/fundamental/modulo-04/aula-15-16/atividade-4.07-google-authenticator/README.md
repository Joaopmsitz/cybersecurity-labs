# Activity 4.07 — Exploring Google Authenticator on Kali Linux

> **Program:** Hackers do Bem  
> **Stage:** Fundamental — Module 04  
> **Class:** 15–16  
> **Environment:** Kali Linux  
> **Status:** Completed

## Objective

Configure Google Authenticator on Kali Linux using TOTP (Time-based One-Time Password).

The activity demonstrates the generation of a secret key, linking that key to an authenticator application through a QR code, and generating temporary codes used as a second authentication factor.

The laboratory was performed in a controlled academic environment.

## Environment

- **Operating system:** Kali Linux
- **User:** `root` during authenticator configuration
- **Application:** Google Authenticator
- **Method:** TOTP
- **Code validity period:** Approximately 30 seconds
- **Additional device:** Smartphone

The VM access credentials, TOTP secret key, temporary codes, and recovery codes used in the laboratory are not published in this README.

## Procedure

### 1. Obtain Administrative Access

A terminal was opened, and superuser access was obtained:

```bash
sudo -i
```

The password used belongs to the laboratory environment and is not recorded in this document.

### 2. Configure the Time Zone

Before configuring the authenticator, the machine's time zone was set to São Paulo time:

```bash
timedatectl set-timezone America/Sao_Paulo
```

The configuration was then verified:

```bash
timedatectl
```

**Observed output:**

```text
Local time: sáb 2025-09-06 20:46:18 -03
Universal time: sáb 2025-09-06 23:46:18 UTC
RTC time: sáb 2025-09-06 23:46:18
Time zone: America/Sao_Paulo (-03, -0300)
System clock synchronized: yes
NTP service: active
RTC in local TZ: no
```

Correct time synchronization is important for TOTP because the codes are calculated using the current time.

### 3. Initialize Google Authenticator

The program was started on Kali Linux:

```bash
google-authenticator
```

The option to use time-based tokens was selected:

```text
Do you want authentication tokens to be time-based (y/n) y
```

The program then displayed a QR code in the terminal and generated a secret key associated with the configuration.

For security reasons, the key displayed during the laboratory is not reproduced in this README.

The output generated by the program followed this pattern:

```text
Do you want authentication tokens to be time-based (y/n) y
Warning: pasting the following URL into your browser exposes the OTP secret to Google:
  [otpauth URL containing the secret removed]

Your new secret key is: [TOTP SECRET REMOVED]
```

The secret key allows the authenticator application and the server to generate matching TOTP codes.

**Security note:** The secret key and the QR code containing the authentication configuration must be treated as sensitive credentials. Anyone who obtains the secret may be able to generate the same TOTP codes.

### 4. Link Google Authenticator to the Configuration

With Google Authenticator installed on the smartphone, the option to add a new account by scanning a QR code was selected.

The QR code displayed in the Kali terminal was scanned using the application.

After linking the account, Google Authenticator began generating TOTP codes for the configured account.

### 5. Validate the TOTP Code

The code displayed by the application was entered in the Kali terminal when prompted:

```text
Enter code from app (-1 to skip): [TOTP CODE REMOVED]
Code confirmed
```

The program also displayed recovery codes.

These codes are not reproduced in this README because they can serve as alternative credentials for accessing the configured account.

The result:

```text
Code confirmed
```

confirmed that the code generated by the application matched the code expected by Google Authenticator on Kali Linux.

### 6. Configure Security Options

After the code was confirmed, the program prompted for additional configuration options.

The options presented by the laboratory instructions were accepted.

#### Update the Configuration File

```text
Do you want me to update your "/root/.google_authenticator" file? (y/n) y
```

The `.google_authenticator` file stores the information required to configure the authenticator for the user.

#### Restrict Token Reuse

The option to prevent the same token from being used multiple times was enabled:

```text
Do you want to disallow multiple uses of the same authentication
token? ... (y/n) y
```

This setting helps prevent reuse of the same code during its validity window.

#### Time Window Tolerance

The option related to compensating for possible time differences between the client and server was also enabled:

```text
Do you want to do so? (y/n) y
```

The purpose of this setting is to allow a tolerance window for differences in time synchronization.

#### Rate Limiting

Finally, rate limiting for authentication attempts was enabled:

```text
If the computer that you are logging into isn't hardened against brute-force
login attempts, you can enable rate-limiting for the authentication module.

Do you want to enable rate-limiting? (y/n) y
```

This option limits the number of permitted attempts within a given period, helping to hinder automated brute-force attempts.

## 7. How TOTP Works

TOTP (Time-based One-Time Password) generates temporary codes using a shared secret key and the current time.

The process observed in the laboratory can be represented as follows:

```text
Secret Key
      │
      ├───────────────┐
      │               │
      ▼               ▼
Kali Linux       Google Authenticator
      │               │
      │   Same time    │
      └───────┬───────┘
              ▼
         TOTP Code
          Temporary
```

The server and the application do not need to exchange the generated code over the network to calculate the expected value. Both use the same secret key and a time reference to calculate the code.

## Concepts Practiced

### TOTP

Time-based One-Time Password is an authentication mechanism based on temporary codes calculated from a secret key and the current time.

### Second Authentication Factor

TOTP can be used as a second factor in addition to a traditional password.

In this scenario, even if a password is known, access may also require the temporary code generated by the authenticator.

### Secret Key

The secret key is used by both sides to generate matching TOTP codes.

It must be protected as a credential.

### QR Code

The QR code displayed by `google-authenticator` provides a convenient way to transfer the token configuration to the authenticator application.

### Time Synchronization

Because TOTP depends on time, significant differences between the server's clock and the authenticator device's clock can cause validation failures.

For this reason, the activity began by configuring and verifying the machine's time zone.

### Rate Limiting

Rate limiting reduces the number of authentication attempts permitted within a given period, helping to defend against automated brute-force attempts.

## Results

The activity successfully configured Google Authenticator on Kali Linux and linked it to a smartphone using TOTP.

The following tasks were performed:

- Configured the Kali Linux time zone.
- Started `google-authenticator`.
- Enabled time-based tokens.
- Generated a TOTP configuration.
- Displayed the QR code in the terminal.
- Registered the token in the Google Authenticator application.
- Generated a temporary code.
- Validated the code on Kali Linux.
- Configured protection against token reuse.
- Configured tolerance for time differences.
- Enabled rate limiting.
- Completed the second-factor configuration.

The activity demonstrated how a TOTP authenticator can complement password-based authentication.
