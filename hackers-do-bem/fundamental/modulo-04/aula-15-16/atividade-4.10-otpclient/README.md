# Activity 4.10 — OTPClient

> **Program:** Hackers do Bem  
> **Stage:** Fundamental — Module 04  
> **Class:** 15–16  
> **Environment:** Kali Linux  
> **Status:** Completed

## Objective

Use OTPClient to store a TOTP secret in a protected database and generate temporary authentication codes.

The activity demonstrates how to manually register a TOTP token and view the code generated by the application.

**Security note:** The TOTP secret, database password, QR code, temporary authentication codes, and backup files are not recorded in this README.

## Environment

- Kali Linux
- OTPClient
- Google Authenticator
- TOTP (Time-based One-Time Password)
- Encrypted database

## Procedure

### 1. Open OTPClient

The application was launched from the terminal:

```bash
otpclient
```

The following message was displayed during startup:

```text
[WARNING] your OS's memlock limit may be too low for you (current value: 8388608 bytes).
This may cause issues when importing third parties databases or dealing with tens of tokens.
For information on how to increase the memlock value, please have a look at https://github.com/paolostivanin/OTPClient/wiki/Secure-Memory-Limitations
```

#### Interpretation

The warning indicates that the system's locked-memory limit (`memlock`) may be low.

The `memlock` limit relates to the ability to keep certain memory regions from being swapped to disk. OTPClient uses memory-protection mechanisms to reduce the exposure of sensitive information.

This warning did not prevent the application from running in the laboratory.

### 2. Create the Database

A new database was created in OTPClient:

```text
NewDatabase.enc
```

The file was saved in the following directory:

```text
/home/aluno/Documentos
```

A password was set to protect the database.

The password used in the laboratory is not published in this document.

After creation, the database was unlocked to allow the token to be registered.

### 3. Generate a New TOTP Secret

In another terminal, the following command was executed:

```bash
google-authenticator
```

The option to use time-based tokens was selected:

```text
Do you want authentication tokens to be time-based (y/n) y
```

Google Authenticator generated a new TOTP secret.

The actual secret was used only during the laboratory configuration and has been omitted from this README.

### 4. Add the Token to OTPClient

In OTPClient, the following option was selected:

```text
+
```

The manual token configuration option was then selected.

The fields associated with the account, issuer, and TOTP secret were completed.

The secret generated by `google-authenticator` was entered in the corresponding field:

```text
Secret
```

The actual value is not reproduced in this document.

### 5. View the TOTP Code

After the token was saved, its entry appeared in OTPClient.

Selecting the token displayed information such as:

```text
Type
Account
Issuer
OTP Value
Validity
```

The `OTP Value` field displays the temporary code currently generated by OTPClient.

The validity field indicates how much time remains before the code is renewed.

The TOTP code is calculated using the registered secret and the current time:

```text
TOTP Secret + Current Time
          ↓
         TOTP
          ↓
   Temporary Code
```

The OTPClient-generated code can be validated by a compatible system configured with the same secret and a sufficiently synchronized clock.

## Concepts Practiced

### OTP

One-Time Password (OTP) is a password intended to be used once or within a limited period.

This activity used TOTP, in which the code is calculated based on time.

### TOTP

Time-based One-Time Password uses a shared secret and the current time to generate temporary codes.

For this reason, the secret must be protected. Anyone who obtains it may be able to generate the same TOTP codes.

### OTPClient

OTPClient allows users to store OTP tokens in a protected database and use those tokens to generate authentication codes.

In this laboratory, the secret was registered manually, and the code was generated by the application.

### `NewDatabase.enc` Database

The file created during the laboratory serves as protected storage for the tokens registered in OTPClient.

A backup file was also created during the activity.

These files must not be published in public repositories because they may contain information needed to recover the registered tokens.

**Security note:** Database encryption does not eliminate the need to protect the database password, backups, and TOTP secrets. All copies should be treated as sensitive data.

### 6. Clean Up the Laboratory

After completing the activity, the files created in the directory were inspected:

```bash
sudo -i
cd /home/aluno/Documentos
ls
```

**Observed output:**

```text
NewDatabase.enc  NewDatabase.enc.bak  QRcode.png
```

The files generated exclusively for the laboratory were removed:

```bash
rm *
```

The system requested confirmation:

```text
zsh: sure you want to delete all 3 files in /home/aluno/Documentos [yn]? y
```

**Warning:** `rm *` is a destructive command. It was used here only during laboratory cleanup, after verifying that the files in the directory were artifacts generated by the activity. In a real environment, it is safer to remove specific files by name.

## Results

A protected database was created in OTPClient, and a TOTP token generated by `google-authenticator` was registered manually.

OTPClient successfully generated and displayed the temporary code along with its account, issuer, type, and validity information.

The activity demonstrated the following workflow:

```text
Google Authenticator
        ↓
     TOTP Secret
        ↓
      OTPClient
        ↓
  Protected Database
        ↓
 Temporary TOTP Code
```

The exercise reinforced how an authenticator application can store a TOTP secret and generate temporary codes locally, provided that the secret and time reference are consistent with those used by the validating system.
