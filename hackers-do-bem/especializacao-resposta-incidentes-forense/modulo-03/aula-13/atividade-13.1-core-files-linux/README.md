## 3. Core Dump and Memory Forensics Concepts

### Core Dump

A core dump is a file generated by the operating system when a process terminates abnormally under conditions that permit core dumping.

It can preserve portions of the process memory and other information useful for investigating the failure.

Core files are commonly used by developers and system administrators to diagnose application crashes.

In digital forensics, the same artifacts can contain information about a program's execution context, environment variables, paths, and data that was present in process memory.

### Segmentation Fault

A segmentation fault occurs when a process attempts to access memory in an invalid or unauthorized way.

Examples include:

- Accessing memory outside an array's valid range.
- Dereferencing an invalid pointer.
- Writing to memory that is not accessible to the process.
- Using invalid memory addresses.

The operating system terminates the affected process and may generate a core dump.

### RLIMIT_CORE and ulimit

Linux controls core dump size through the process resource limit `RLIMIT_CORE`.

The shell command:

```bash
ulimit -c unlimited
```

sets the core file size limit to unlimited for the current shell and its child processes, subject to system-wide core dump configuration.

This setting is necessary in the course environment because the default core dump limit may be zero.

### GCC Debug Information

The source file is compiled using:

```bash
gcc -g -Wall -o genpass genpass.c
```

The options are:

| Option | Function |
|---|---|
| `gcc` | Invokes the GNU C Compiler |
| `-g` | Includes debugging information in the executable |
| `-Wall` | Enables a broad set of compiler warnings |
| `-o genpass` | Specifies the output executable name |
| `genpass.c` | C source file to compile |

Debug information can help a debugger correlate machine instructions with source-level information.

### strings

The `strings` utility searches a file for printable character sequences.

When applied to a core dump, it can reveal readable text that was present in the captured memory.

It does not reconstruct the complete process state and does not interpret memory structures automatically. It is a preliminary examination technique that helps identify potentially relevant strings.

## 6. Technical Analysis

### Input Validation Failure

The program declares:

```c
int i, nr, array[10];
```

This creates an array containing ten integer positions:

```text
array[0] through array[9]
```

However, the initialization loop is:

```c
for (i = 0; i < 9; i++) {
    array[i] = rand() % 99999999;
}
```

The loop initializes only the indexes:

```text
array[0] through array[8]
```

The program later reads:

```c
array[nr]
```

without checking whether `nr` is a valid index.

There are therefore two problems:

1. A value greater than 9 can access memory outside the array.
2. The value 9 is within the declared array size but corresponds to an element that the loop did not initialize.

The program's prompt says that the valid range is 0 to 9, but the implementation does not correctly initialize all ten positions or validate the input.

### Why the Input Produces a Failure

The input:

```text
123123 123 1 23123 12
```

contains several numbers separated by spaces.

The `scanf` expression:

```c
scanf("%d", &nr);
```

reads the first integer token, which is:

```text
123123
```

The remaining values do not make the first integer valid.

When the program evaluates:

```c
array[123123]
```

it accesses a position far beyond the allocated array.

This is undefined behavior in C. A segmentation fault is a possible consequence, as observed in the laboratory.

The same invalid access is not guaranteed to cause an identical result on every system because undefined behavior can produce different outcomes.

### Purpose of the -g Compiler Option

The `-g` flag adds debugging information to the executable.

This can provide additional context for debuggers and developers when examining the crash.

The `-Wall` flag enables compiler warnings, although not every logical or runtime error is necessarily detected during compilation.

### What a Core File Can Reveal

A core file may preserve information from the process memory, including:

- Application strings.
- Loaded library references.
- Executable paths.
- Environment variables.
- User and execution context.
- Data present in memory at the time of failure.

The precise contents depend on the process, operating system, core dump configuration, and the memory regions preserved.

### strings Limitations

The `strings` utility extracts printable sequences.

It does not provide a complete reconstruction of the process state.

A string identified in a core dump must be correlated with the file, memory layout, program behavior, and other forensic evidence.

### Security Implications

Core dumps can contain sensitive information.

They may preserve account names, environment variables, paths, application data, and potentially other data that was present in process memory.

Forensic handling should therefore protect core files as sensitive evidence.
