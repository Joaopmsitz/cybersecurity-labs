## 1. Objective

Investigate a brute-force authentication attack against the DVWA application and identify the evidence recorded by the web server.

The exercise uses the DVWA **Brute Force** module.

Hydra is used in the controlled laboratory to test combinations of usernames and passwords supplied through wordlists.

The investigation then examines Apache's access log to identify the repeated authentication requests and the User-Agent associated with the tool.

The main objectives are:

- Prepare username and password wordlists.
- Understand the use of Hydra in a controlled authentication test.
- Identify successful authentication combinations.
- Examine Apache access log entries.
- Identify the source IP, request parameters, timestamp, and tool signature.
- Correlate the results with the authentication activity observed in DVWA.

## 3. Technical Concepts

### Brute-Force Authentication

A brute-force attack attempts multiple credential combinations until a valid username and password pair is identified.

The effectiveness of this approach depends on several factors, including:

- Password complexity.
- Account lockout policies.
- Login rate limits.
- Multi-factor authentication.
- Monitoring and detection.
- The size and quality of the wordlists.

### Wordlists

A wordlist is a text file containing candidate usernames or passwords.

The laboratory uses two separate files:

```text
users.txt
pass.txt
```

The first contains candidate usernames, and the second contains candidate passwords.

With eight usernames and seven passwords, the exercise evaluates:

```text
8 × 7 = 56 combinations
```

### THC Hydra

Hydra is a network login auditing utility that supports multiple authentication protocols.

The practical exercise uses its HTTP form module against the DVWA Brute Force endpoint.

Hydra can submit candidate usernames and passwords and evaluate server responses according to the configured success or failure condition.

### HTTP Authentication Logs

Apache can record HTTP requests and their associated query parameters.

A brute-force tool may generate many requests to the same login endpoint within a short time interval.

The User-Agent may also identify the automated client.

The activity uses these characteristics to identify requests generated by Hydra.

### tac, grep, and more

The following command-line utilities are used during the log investigation:

| Utility | Function |
|---|---|
| `tac` | Displays file lines in reverse order |
| `grep` | Filters lines containing a specified pattern |
| `more` | Displays output one screen at a time |

The command pipeline allows the examiner to inspect recent entries containing the Hydra User-Agent signature.

## 6. Technical Analysis

### Authentication Pattern

A brute-force attack differs from normal interactive login behavior because it produces repeated authentication attempts.

The activity generated multiple requests to the same endpoint while varying the username and password parameters.

The short interval between requests is consistent with automated credential testing.

### Hydra User-Agent

The Apache log contains:

```text
Mozilla/5.0 (Hydra)
```

This provides a useful indicator that the HTTP requests were generated by Hydra.

The User-Agent can be modified by some tools, so it should not be treated as a unique or definitive signature.

It is one indicator among several.

### Source Address and Request Volume

The requests originated from:

```text
192.168.98.30
```

The web server address was:

```text
192.168.98.10
```

The repeated requests targeted:

```text
/dvwa/vulnerabilities/brute/
```

The varying username and password parameters demonstrate systematic credential testing.

### HTTP Status and Response Size

The sample requests returned HTTP status:

```text
200
```

A successful HTTP response does not necessarily indicate successful authentication.

The response size can also vary between login outcomes.

For this reason, the examiner should correlate HTTP status, response content, application behavior, and Hydra's reported results.

### Log Ordering with tac

The command:

```bash
tac /var/log/apache2/access.log
```

displays the most recently recorded lines first.

Combining it with:

```bash
grep Hydra
```

reduces the amount of data that must be reviewed manually.

The `more` utility makes it easier to inspect large output.

### Session Cookie Accuracy

The course emphasizes that Hydra must use the correct DVWA session cookie.

An incorrect cookie can produce misleading results.

For forensic documentation, the session value should remain private and should not be committed to a public repository.

### Timeline Consideration

The supplied Hydra console output identifies a run on:

```text
2024-07-13 23:50:19
```

The example Apache access log records are dated:

```text
10/Jul/2023
```

These dates do not represent the same execution time.

The source material may contain excerpts from different laboratory runs or snapshots.

They should not be combined into a single chronological incident timeline without confirming their provenance.

### Defensive Recommendations

Controls against brute-force attacks include:

- Rate limiting authentication requests.
- Account lockout or progressive delays.
- Multi-factor authentication.
- Monitoring repeated failed logins.
- Alerting on unusual request volume.
- Restricting exposed authentication endpoints.
- Preventing weak and reused passwords.
- Reviewing authentication logs and source IP patterns.
- Avoiding unnecessary disclosure of authentication response details.

The activity demonstrated a brute-force authentication test against the DVWA application.
