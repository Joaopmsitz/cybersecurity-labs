## 1. Objective

Investigate a reflected Cross-Site Scripting (XSS) vulnerability in DVWA and examine the HTTP evidence generated by the test.

The exercise uses the DVWA **XSS (Reflected)** module.

The attacker submits JavaScript through a web application input field. The vulnerable application includes the input in its response without safely encoding it, causing the browser to interpret the injected content as executable JavaScript.

The activity also demonstrates how browser session information can be exposed through injected script execution and how a local HTTP server can record incoming requests in the controlled laboratory.

The investigation then examines Apache's access log to identify the requests associated with the reflected XSS test.

## 3. Technical Concepts

### Cross-Site Scripting

Cross-Site Scripting is a web application vulnerability in which untrusted content is interpreted as executable content by a user's browser.

XSS can allow an attacker to manipulate page content or cause browser-side actions in the context of the vulnerable application.

Potential consequences include:

- Unauthorized actions within a user's session.
- Exposure of browser-accessible information.
- Session compromise.
- Redirection to external resources.
- Manipulation of application content.

### Reflected XSS

Reflected XSS occurs when untrusted input is included in an HTTP response without appropriate output encoding or sanitization.

The input is generally delivered through a request parameter or form submission.

The application reflects the supplied content in the response, and the victim's browser interprets it in the context of the vulnerable site.

This type of XSS is also called non-persistent XSS because the injected content is not permanently stored by the application.

### JavaScript and document.cookie

JavaScript running in a page can access cookies that are available to scripts.

The following browser property is relevant:

```javascript
document.cookie
```

Cookies configured with the `HttpOnly` attribute are not exposed through this JavaScript property.

This attribute reduces the impact of some cookie-theft scenarios but does not eliminate the underlying XSS vulnerability.

### Python HTTP Server

The course uses Python's built-in HTTP server to receive requests in the isolated lab.

The command is:

```cmd
python -m http.server 8080
```

The server listens on port `8080` and records incoming HTTP requests in its terminal output.

A request to a path that does not correspond to an existing file may return HTTP 404 while still appearing in the server log.

### Apache Access Logs

Apache's access log records requests sent to the vulnerable application.

The log can preserve URL parameters containing encoded JavaScript, which makes it useful when reconstructing reflected XSS tests.

## 4. Procedure

### Step 1 — Reset the Application Session

Before starting the activity, the course instructed the user to open Cookie-Editor, delete the `PHPSESSID` cookie, and authenticate again.

This ensured that the browser was using a fresh DVWA session.

The application was accessed through:

```text
http://192.168.98.10/dvwa
```

The **XSS (Reflected)** module was selected.

### Step 2 — Test Reflected JavaScript Execution

The module presented a field for entering a name.

The following harmless proof-of-execution test was used:

```html
<script>alert(document.cookie);</script>
```

The application returned a response that caused the browser to display a JavaScript alert.

The alert exposed the cookie information available to JavaScript in the current session.

This demonstrated that the application was reflecting untrusted input as executable browser content.

### Step 3 — Start the Local HTTP Server

A Command Prompt window was opened on `forenseWin`.

The following command was executed:

```cmd
python -m http.server 8080
```

The course output showed:

```text
Serving HTTP on 0.0.0.0 port 8080 (http://0.0.0.0:8080/) ...
```

The server was prepared to receive HTTP requests on port `8080`.

### Step 4 — Observe the Browser-Side Request

The next phase of the laboratory demonstrated how JavaScript executing in the vulnerable page could cause the browser to send a request to the controlled HTTP server.

The collector destination used in the exercise was:

```text
192.168.98.30:8080
```

The specific session-exfiltration JavaScript is not reproduced in this public README.

The forensic indicator is the resulting HTTP request, which contains a cookie-related path parameter.

The local server recorded:

```text
Serving HTTP on 0.0.0.0 port 8080 (http://0.0.0.0:8080/) ...
192.168.98.30 - - [10/Jul/2023 01:53:43] code 404, message File not found
192.168.98.30 - - [10/Jul/2023 01:53:43] "GET /cookie=PHPSESSID=[REDACTED];%20security=low HTTP/1.1" 404 -
192.168.98.30 - - [10/Jul/2023 01:53:43] code 404, message File not found
192.168.98.30 - - [10/Jul/2023 01:53:43] "GET /favicon.ico HTTP/1.1" 404 -
```

The PHP session identifier is redacted because session tokens should not be published in a public repository.

The HTTP 404 response does not mean that the request was not received. The server logged the incoming request even though the requested resource did not exist.

### Step 5 — Investigate the Apache Access Log

The investigation returned to the Linux server hosting DVWA.

A root shell was opened:

```bash
sudo su
```

The access log was filtered for entries containing the word `cookie`:

```bash
cat /var/log/apache2/access.log | grep cookie
```

The supplied course output includes the following record:

```text
192.168.98.30 - - [10/Jul/2023:01:12:07 +0000] "GET /dvwa/vulnerabilities/xss_r/?name=%3Cscript%3Ealert%28document.cookie%29%3B%3C%2Fscript%3E HTTP/1.1" 200 1763
```

Another entry records a request containing JavaScript-related content:

```text
192.168.98.30 - - [10/Jul/2023:01:38:33 +0000] "GET /dvwa/vulnerabilities/xss_r/?name=%3Cscript%3Edocument.cookie%3C%2Fscript%3E HTTP/1.1" 200 1757
```

The course material also shows requests associated with the transition from the reflected XSS page to other DVWA pages.

The log entries demonstrate that the injected content was submitted through HTTP request parameters.

## 6. Technical Analysis

### Why the Vulnerability Is Reflected

The injected JavaScript is supplied through a request parameter.

The application includes this content in the response without encoding it as plain text.

The browser then processes the returned response and executes the script.

Unlike stored XSS, the malicious content is not necessarily persisted in a database.

The request and response cycle is the key characteristic of this vulnerability.

### Session Cookie Exposure

The laboratory demonstrates that JavaScript can access cookies exposed through the browser's `document.cookie` property.

If session cookies lack appropriate protection, XSS can expose session information.

The `HttpOnly` cookie attribute prevents JavaScript access to the cookie through `document.cookie`.

The `Secure` attribute restricts cookie transmission to secure transport, while `SameSite` helps control cross-site cookie behavior.

These cookie attributes are important defenses, but they do not replace proper XSS prevention.

### Why the Local HTTP Server Returned 404

The course server recorded:

```text
404 File not found
```

The important evidence is that the HTTP request arrived and appeared in the server output.

A 404 response only indicates that the requested path was not available as a file or resource on the local Python server.

It does not invalidate the fact that the request was received.

### Apache Log Interpretation

The access log provides evidence of the request sent to the vulnerable application.

The relevant record includes:

| Field | Evidence |
|---|---|
| Source IP | `192.168.98.30` |
| Timestamp | `10/Jul/2023` |
| HTTP Method | `GET` |
| Application Path | `/dvwa/vulnerabilities/xss_r/` |
| Request Parameter | `name` |
| Payload Indicator | Encoded `<script>` content |
| HTTP Status | `200` |
| User-Agent | Firefox 114.0 on Windows 10 |

These fields help reconstruct the client activity and identify the browser used during the test.

### Detection and Prevention

Defensive controls include:

- Context-aware output encoding.
- HTML sanitization when user-authored markup is required.
- Avoiding unsafe insertion of untrusted content into the DOM.
- Using Content Security Policy as an additional layer.
- Setting appropriate cookie attributes.
- Monitoring unusual script-bearing query parameters.
- Reviewing requests to vulnerable application endpoints.

## 7. Results and Interpretation

The activity demonstrated reflected XSS in the DVWA application.

The JavaScript proof-of-execution caused the browser to display an alert containing cookie information accessible to scripts.

The local HTTP server also recorded an incoming request associated with cookie-related information.

The Apache access log preserved the requests sent to the XSS endpoint, including URL-encoded JavaScript.

These records provide evidence that can be correlated with the browser activity and the local collection server output.
